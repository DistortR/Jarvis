# Jarvis implementation plan

**Goal** — Say “Jarvis,” ask a question in English, and hear an English reply while your current app stays in focus.

**Architecture** — A Python background process reads one PipeWire microphone stream. openWakeWord detects the wake phrase locally. Jarvis chimes, collects the request until silence, passes a temporary WAV to Voxtype, sends the resulting text to the configured agent backend, and plays its final reply through Piper. Codex is the first backend.

## Switching agents

- Put agent integration in `agent.py` behind a small `reply(transcript: str) -> str` interface. Each backend owns its connection and conversation state. The voice pipeline only passes a transcript and receives reply text.
- Select the backend in the service configuration. Start with `codex` as the default. When adding a local backend, use `ollama` as the runtime and make the model configurable so it can run a Qwen model or another installed model. Restart the service to switch backends.
- Keep conversation state separate by backend. A switch starts or resumes a conversation with the selected backend, with no automatic history transfer or cloud fallback. Ollama and a local model are only needed when adding that backend.

## What we need

- The installed Voxtype, Codex CLI, PipeWire tools and uv. Jarvis explicitly uses English Whisper base.en for microphone transcription. Codex can use the existing ChatGPT login and needs internet access.
- An isolated Python environment with a version supported by the audio dependencies. System Python is 3.14, so verify wheel availability before choosing the version.
- An openWakeWord “Jarvis” model, a local voice activity detector for the end of the request, Piper and the Jarvis British English voice.
- One short microphone and speaker test with the user to tune recognition and pick a comfortable playback voice.

## Build order

1. **Prove the text-to-voice path.** In `agent.py`, implement the Codex backend using stdin and capture its final reply. Use a dedicated session ID for follow-ups and a read-only sandbox for the first version. In `jarvis.py`, call the configured backend and play its reply with Piper. Prove the same voice pipeline works with a stub backend first, then send a short live prompt during the approved test. Confirm the reply is audible with the terminal closed.
2. **Add hands-free recording.** Capture 16 kHz mono PCM through PipeWire. Start collecting speech after the chime, stop after roughly one second of trailing silence and cap the recording at 20 seconds. Use a private temporary WAV and `voxtype transcribe`. Test English speech, a pause mid-sentence and silence. Silence or a failed transcription should return Jarvis to idle without a Codex request.
3. **Wire in the wake phrase.** Feed the idle microphone stream to openWakeWord. Handle one request at a time and pause detection through the chime, Codex turn and Piper playback. Drop old audio before returning to idle. Test “Jarvis” at normal desk distance, ordinary conversation, repeated activations and speaker playback.
4. **Run it at login.** Add `jarvis.service` for systemd user startup and `README.md` for setup, mute/stop and troubleshooting. Show a desktop status when the microphone is listening or processing a request. Test starting, stopping and logging back in, then make two English requests with the agent window closed and verify the second request can refer to the first.

## Acceptance checks

Use a small `test_jarvis.py` suite for silence, failed subprocesses, turn overlap, backend selection and resuming idle after playback. Test that an unknown backend fails clearly and switching backends keeps the voice pipeline and conversation boundaries intact. Use local recordings for repeatable audio tests. When the selected backend is unavailable, Jarvis should report the failure and return to idle. Wake and request audio stay on the PC. Codex receives the request transcript when selected. Verify offline operation when the local backend is added.
